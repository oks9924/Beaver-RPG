# 개발 에이전트 전달용 — 전투 애니메이션 연결

기존 제작 MD를 게임 규칙의 기준으로 유지하고 아래 에셋을 연결해줘. 이 작업은 설치형 클라이언트와 독립 전용 서버에서 진행한다.

## 기존 v1과 함께 쓰기

1. `beaver_combat_v2`를 `res://beaver_combat_v2/`에 복사한다.
2. 플레이어 직업은 v1 리소스를 계속 사용한다. 적·보스의 기존 `enemy_*`, `boss_*` ID는 유지하고, 시각 리소스 매핑만 v2의 `.tres`로 바꾼다.
3. 이 팩에 적·보스 기본 자세도 포함되어 있으므로 해당 15개 SpriteFrames는 대기와 전투 상태를 함께 가진다.
4. 각 기믹은 `IC-01`~`IC-05`, `TF-01`~`TF-05`, `RK-01`~`RK-05` ID로 관리한다. 장치의 시각 리소스는 `mechanic_ic_01` 같은 별도 에셋 ID다.
5. 파일 경로를 저장 데이터에 박지 않는다. 직업/적/보스/기믹 ID를 저장하고 경로는 레지스트리에서 해결한다.

## 공격 연결

서버 공격 상태를 준비→활성→회복으로 정의하고 서버 시각·행동 ID·진행률을 클라이언트에 전달한다. 클라이언트는 준비 프레임 0~1, 시각적 공격 프레임 2, 회복 프레임 3을 맞춰 보여준다.

`visual_contact_frame=2`는 아티스트가 제안한 시각적 접촉 위치다. `frame_changed`에서 피해를 직접 주거나, 프레임 수를 공격 횟수로 세지 않는다. 피해·발사·무적·경직은 서버가 결정한다. 4인 클라이언트의 FPS 차이가 결과를 바꾸면 안 된다.

돌진과 점프의 월드 이동은 서버의 이동 경로를 따른다. 시트는 제자리 키포즈이며 이미지의 몸 위치 변화로 월드 좌표를 움직이지 않는다. 점프 그림을 매 프레임 발밑에 강제로 붙이면 떠오르는 느낌이 줄어들 수 있으므로 지면 그림자와 시각 높이를 별도 노드로 다듬는다.

마우스/타깃의 정확한 각도와 4방향 몸 이미지는 분리한다. 일부 키포즈는 3/4 각도이므로 창 끝이나 집게 끝 픽셀을 충돌선으로 사용하지 않는다. 투사체·급류·혀·부채꼴·원형 범위는 서버의 실제 조준 방향과 범위에 맞춰 그린다.

## 기믹 연결

각 기믹 인스턴스는 최소 `mechanic_id`, `instance_id`, `state`, `progress`, `target_ids`, `phase_start_tick`, `phase_duration_ticks`, `revision`을 갖는다. 파티/원정별 상태를 분리하고, 과거 revision의 이벤트로 이미 성공한 장치가 되돌아가지 않게 한다.

| 서버 상태/이벤트 | 장치 연출 | 보스 몸체 |
|---|---|---|
| 시작·상호작용 진행 | activation_fixed를 진행률에 맞춰 표시 | 필요할 때 mechanic_channel_<방향> |
| 해결 대기 | activation 마지막 상태 유지, 논리 조건 대기 | 현재 서버 전투 상태 유지 |
| 목표 성공 | success_fixed 단발, 성공 상태 유지 | 기획상 경직/노출 효과가 있을 때 weakpoint_exposed_<방향> |
| 제한 실패 | failure_fixed 단발, 해당 장치의 재시도 상태로 전환 | 실패용 전투 상태를 서버에서 선택 |
| 중단·보스 사망·원정 종료 | 잔여 연출/장치 정리 | 정리 상태로 전환 |

시전 애니메이션 끝에서 성공을 자동 판정하지 않는다. 실패를 성공 시퀀스의 역재생으로 처리하지 않는다. 성공한 기둥·수로·제어 장치는 서버에 진행도를 보존하고, 해당 전투 중 임의 초기화하지 않는다.

공통 약점 노출 포즈는 시각 반응의 출발점이다. 실제 약점 위치와 활성 여부는 보스의 약점 노드와 별도 윤곽/마커로 보여준다. 뒤를 보는 프레임에 앞쪽 코어를 억지로 그려 넣지 않는다.

조합형 장치 그림을 그대로 쓸 수 있는 프로토타입을 우선 구성한다. 정식 단계에서 실제로 독립 움직이는 씨앗·쐐기·고리·수로 조각·뿌리는 각각의 노드/리소스로 분리한다. 장치 애니메이션이 공간적으로 떨어진 여러 노드의 상호작용을 대신 수행하지 않는다.

## 1~4인 연결 규칙

인원에 따라 애니메이션을 빠르게 틀거나 몸체를 단순 확대하지 않는다. 같은 에셋 ID를 사용하면서 아래 항목을 데이터로 바꾼다.

- IC-01 성공 목표 수는 인원만큼 복제하지 않는다. 준비와 유도 분담이 빨라질 수 있게 한다.
- IC-03은 혼자 잡혀도 고리·쐐기를 조작할 수 있어야 한다. 장치 활성 범위를 외부 구조자 전용으로 잠그지 않는다.
- IC-04의 후보 통로는 1인 2개, 다인 최대 3개다. IC-05는 한 줄로 진행 가능하며 다인에서 최대 두 줄의 병렬 이점을 준다.
- TF-01 정화 지점과 TF-04 혼합통은 1인 1개, 다인 최대 2개다. 역할 담당자 다운/이탈 시 인계 가능한 진행도를 유지한다.
- TF-02/03/05는 연결망·입력 장치·반딧불 경로를 조절하며, 단독 순회와 국지 복구를 허용한다.
- RK-01/02는 정보 분담·분기·전장 압박을 조절한다. 필수 수로 조각을 4배로 늘리지 않는다.
- RK-03은 뿌리 1~2개, RK-04는 잔향 1~2개, RK-05는 우선순위 지점 2~3개를 사용한다.
- 인원 증감으로 이미 성공한 장치를 초기화하거나 진행 중 물체를 사라지게 하지 않는다. 서버에서 안전한 단계에 변경을 적용한다.

체력·경직·실패 완충·공격 예산은 기존 MD의 별도 난이도 데이터로 조절한다. 시각 리소스 수를 난이도 자체로 취급하지 않는다.

## 엔진 연결과 완료 기준

`AnimatedSprite2D`에 `.tres`를 넣고 `centered=false`, `offset=-anchor_px`를 적용한다. 일반 적 `(64,106)`, 보스 `(256,424)`, 장치 `(128,212)`가 시작값이다. 시각 배율과 충돌 노드 크기는 별도로 둔다.

`CombatVisual.gd`의 `set_phase_progress()`는 서버 단계 진행률을 받아 프레임을 선택하는 예제다. 네트워크 시간 보정과 상태 머신은 게임 프로젝트가 맡는다. `play_named(..., true)`는 새 이벤트가 도착했을 때만 호출한다. 매 프레임 재시작하지 않는다.

리소스가 JSON 경로로 동적 로딩될 때도 export 대상에서 폴더가 빠지지 않도록 설정하고 Windows 실행 파일에서 실제 확인한다. 서버 빌드는 이 시각 자료가 없어도 전투 판정 데이터를 로딩할 수 있어야 한다.

완료 검수:

1. 15개 몸체의 기본 자세와 공격/보스 상태를 4방향으로 재생한다.
2. 15개 기믹의 진행·성공·실패를 서로 다른 서버 이벤트로 재생한다.
3. 성공한 장치의 상태가 반복 애니메이션 때문에 다시 초기화되지 않는지 확인한다.
4. 1인·4인과 중간 재접속에서 같은 논리 상태가 같은 연출로 복원되는지 확인한다.
5. 프레임 배율과 FPS를 바꿔도 피해·사거리·쿨다운이 바뀌지 않는지 확인한다.
6. 발 미끄러짐, 신체 비율 변화, 시각적 방향 오차, 잘린 무기·VFX를 실제 배경 위에서 조정한다.

Godot 공식 참고: [AnimatedSprite2D](https://docs.godotengine.org/en/stable/classes/class_animatedsprite2d.html), [SpriteFrames](https://docs.godotengine.org/en/stable/classes/class_spriteframes.html).
